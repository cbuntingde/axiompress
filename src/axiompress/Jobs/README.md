# Durable delivery and scheduling

Migration 0004 is the first Phase 4 module. Run administrator-only `platform-bootstrap.sql` before it, then provision a distinct LOGIN inheriting `axiom_job_runner` and bind its OID to one site in deployment-owned `axiom_jobs.runners`. The identity has only fixed function execution, not direct content, credential, queue or inbox table access. The request authentication login cannot claim jobs. No user session is serialized into work.

Build `tools/axiompress/jobs/Dockerfile` from the repository root. Run the immutable image with read-only root, no capabilities, a private database network, memory/process limits, and only its job password/CA mounted read-only. Configure `AXIOM_JOBS_PG_HOST`, `PG_PORT`, `PG_DATABASE`, `PG_USER`, `PG_PASSWORD_FILE`, `PG_CA_FILE` and `SITE_ID` using that prefix. Database TLS always verifies identity. The CLI accepts one batch bound (1–100; default 32), executes at most twenty seconds per batch and emits only counts. An external service manager/timer invokes bounded batches; there is no hidden WordPress cron or arbitrary callback executor.

Outbox publications fan out to explicit operator-created site/article/installation subscriptions. Use deployment tooling `tools/axiompress/jobs/manage.php describe SITE ARTICLE INSTALL`, `subscribe ... EXPECTED_GENERATION TTL_SECONDS` or `disable ... EXPECTED_GENERATION`. New subscriptions use expected generation 0; updates advance generation. TTL is 60–86400 seconds, and each site is capped at 128 subscriptions. Registration does not approve a plugin package or widen its existing SQLite installation grant. Both current subscription and installation policy must authorize a future broker consumer; the current delivery target is the core-owned metadata inbox, not arbitrary plugin execution or an HTTP callback.

Only publications committed after subscription creation and within the preceding 24 hours are eligible. Each site retains at most 4096 delivery records and 4096 inbox records. A task has a random thirty-second lease and at most ten attempts. Failed or lost leases back off exponentially from ten seconds to one hour, without a database transaction spanning execution. A late/foreign/old lease cannot acknowledge work. Subscription expiry, disable, generation change, withdrawal or superseding publication cancel delivery on recheck. Durable inbox insertion and successful acknowledgement commit atomically and deduplicate event + subscription + generation. Inbox records contain only event/article/revision/time metadata. Actual extension consumption is an explicit later platform API, not an implied event callback.

Dead letters and completed records are retained for seven days. Expired leases are reconciled during polling; terminal records/inbox expire after seven days. Old outbox records are removed only after their 24-hour delivery window and when no delivery still references them. No new lease revives expired authority. Limits fail closed rather than evicting pending work. Delivery is at least once to a deduplicated inbox; no global event order or exactly-once external effect is promised.

Editors/owners may `POST /v1/articles/{id}/schedule` with exact string fields `expected_revision`, `expected_version`, `due_at` (UTC `YYYY-MM-DDTHH:MM:SSZ`), current cookie/Origin/CSRF and an idempotency key. Due time must be in the next thirty days. `DELETE` on that route with `{}` cancels. New schedules are bounded to 128 per site. A scheduler intent records actor ID, credential fingerprint and revision/version expectations. At execution it checks the current active account/membership, publisher role, credential fingerprint and article expectations under locks. Password/role/account revocation or a competing edit prevents publication. Publishing, outbox emission and intent completion are atomic. Scheduler authority is a fixed core-owned intent; it is not delegation of an editor cookie to a plugin.

Migration mapping: the inherited cron option, arbitrary cron hooks/callbacks and plugin transient queues are not imported or executed. Supported external schedules will need an explicit Phase 5 mapping to reviewed fixed operations; unsupported hooks must be reported. Operational audit, media jobs, inbox consumer API and administration views are subsequent Phase 4 modules. This first module does not complete Phase 4.

Run the expanded database harness for actual PostgreSQL lease/retry/deduplication, cross-site/function-only permissions, revocation, scheduling and restart checks. Phase 3 authentication/content/public read and full isolated-plugin acceptance remain required regressions.
