# Domain command/event design contracts

The implemented worker protocol remains axiompress.plugin/0.1 in ../protocol. Its manifest enables content.read and component.render only. The native HTTP API has separate core-owned session and article commands; plugins cannot invoke them through this protocol. Neither endpoint accepts the design contracts here. They cannot grant authority merely by satisfying a schema.

domain-design.schema.json versions the architectural shapes for content.propose_revision, content.published.v1 and operator-owned service grants. Its distinct API name prevents confusion with an enabled runtime. Commands cannot carry actor/site/installation claims, SQL, callbacks, publication status or HTML. Trusted connection/invocation context supplies identity. Byte framing/UTF-8/duplicate-key/depth limits still apply at transport boundaries; JSON Schema string length alone is not a byte-allocation limit.

A proposed revision requires content.write, current actor edit permission, explicit resource scope, expected revision and current installation generation. It does not publish. Canonical request digest and idempotency outcome scope is site + installation + actor/service + operation + key. Reauthorization precedes replay. Same key/different digest conflicts; mutation/outbox/outcome commit atomically. Initial retry retention is seven days; retain an expired-key tombstone for a further seven days and reject reuse during that interval. After complete expiry, deduplication is no longer promised. Bound aggregate key volume and refuse writes when durable capacity cannot satisfy this policy. No DB transaction spans worker execution.

Published events originate only from committed core outbox rows. The schema carries identifiers/revision/time, never content bodies, credentials or a callback URL. Delivery is at least once; no global order. Reauthorize subscription, actor/service, visibility and grant generation on delivery. Disabled installations do not dispatch; subscribers deduplicate event IDs. Initial delivery window is 24 hours with exponential backoff capped at one hour and ten attempts, then operator-visible dead letter retained seven days. Expired/stale events never recover authority from their payload. These are design parameters to verify in the jobs phase, not an implemented queue.

Service grants are operator policy records, not messages accepted from workers. A service identity is distinct from a user, has one site/install, explicit resources/operations, bounded expiry and a monotonically advancing generation. Initial service invocations would be read-only and at most five seconds; grant validity is at most 24 hours and requires explicit renewal. The schema cannot prove current time or issuer authority; the future policy service must enforce these. No delegation, inferred administrator role, arbitrary cron hook or inherited editor cookie is permitted.

Core owns final publication, authentication, sessions and resource policy. Stable error categories remain invalid_request, unauthenticated, forbidden, not_found, conflict, quota_exceeded, deadline_exceeded, unavailable and internal_error; cross-site/private probes disclose no object existence. Plugin mutations and service jobs remain disabled. Core-only HTTP article commands now have their own authorization, idempotency, rollback and revocation tests; this does not enable plugin proposals or event dispatch. The 18-check PostgreSQL experiment proves necessary database primitives and role authentication, not these domain services.
