# Native media boundary

The native HTTP core accepts PNG/JPEG/WebP source bytes into private PostgreSQL quarantine. It checks framing, canonical base64, claimed MIME and magic bytes; it **does not decode images**. Only the separate fixed GD processor decodes them, under gVisor `runsc`, with no network or mounts, UID 10001, read-only root, dropped capabilities, no new privileges, 128 MiB memory, no swap, half a CPU, bounded process/file limits, an 8-second deadline and bounded output. A separate SQL controller uses a function-only site-bound job identity. Neither worker receives SQL credentials, Docker access or user sessions. The trusted host controller owns Docker authority and must be protected as an operator identity.

Source input and regenerated PNG are each limited to 2 MiB; source dimensions are at most 4096 per edge and 8 million pixels. A fresh canvas regenerates a static PNG at most 1600 pixels per edge, discarding source metadata and animation. Original bytes never have a serving URL and are removed after successful processing or terminal rejection. There are at most 100 assets per site. This initial bounded database store is not an unlimited object store.

`/v1/media` requires the native secure session, exact Origin, CSRF and an idempotency key for writes. Authors manage their own images; editors/owners manage site images. Only editors/owners can publish a prepared image. Private file reads reauthorize the current actor. Public reads use only the reader identity and require current site binding, ready state and explicit publication. Responses use a fixed PNG content type, no-store, nosniff and restrictive CSP. Names are metadata, never filesystem paths or response header values.

Media IDs in canonical article blocks belong to the same site. Publication requires referenced images to be ready and public; restoring a revision copies its references. Withdrawing an image immediately removes its public URL even if a published article references it. A missing image renders as unavailable rather than exposing its original or private representation.

The SQL claim is leased for 30 seconds. Expired claims retry with backoff, with a maximum of three attempts. The host controller serializes transformations with a Linux file lock and durably journals create intent **before** contacting Docker. Unknown creation/removal outcomes retain the journal and stop further work. Do not delete that journal to make the error disappear: fence the controller, inspect the exact recorded container name, verify engine quiescence and remove any matching worker before clearing the recovered record. Preserve the lock inode while controllers can run. `owner.lock` alone is normal idle state. Host or engine outages cannot be proven harmless by a decoder exit code.

Run `tools/axiompress/media/run.py --help` for the operator controller contract. Configuration and state must be private operator files on Linux. The dedicated AxiomPress-Linux daemon provides the local acceptance environment; Docker Desktop is not a silent fallback. `tools/axiompress/database/run-checks.py --isolated-media` exercises actual GD transformations in runsc for all three accepted formats, malformed-image rejection and private/public/withdrawn HTTP reads. SQL fixtures test authorization and leases separately and do not claim valid image decoding.

Migration mapping: WordPress attachment metadata and originals must be imported offline into quarantine and explicitly processed. Existing attachment IDs, URLs, serialized metadata and executable image hooks are not runtime contracts. The Phase 5 importer must report unsupported files and rewritten references. Deployments must back up private assets and publication state together; a worker image alone is not a media backup.
